# 三种计划模式与正反向排程：solverplan 里的两次扫描

第 1 章我贴过求解主入口 `commit()` 的三个分支，当时埋了个伏笔：同一套数据、同一张订单，为什么换个"计划类型"，算出来的结果能天差地别——有的模式告诉你订单会晚交，有的模式却坚持所有订单都准时、只是把设备排到了 300% 负荷。这一章我们专门把这组开关拆开，因为**"用哪种模式算"决定了你拿到的计划能不能直接拿去车间执行**，是 APS 使用者必须真正理解、而不是点一下默认按钮的东西。

先讲清楚 frePPLe 有两个相互独立的旋钮，很多人把它们混成一个。第一个是**约束开关 constraints**（一个位掩码），决定计算时考虑哪些现实限制；第二个是**计划类型 plantype**，决定遇到满足不了的需求时引擎采取什么态度。方向上还有一对"反向排程 / 正向排程"的算子。我们一个一个来。

## 约束到底约束了什么：一个位掩码

在 `include/frepple/solver.h` 里，约束的存取函数把这个位掩码暴露得很清楚：

```cpp
void setConstraints(short i) {
  constrts = i & (CAPACITY + PO_LEADTIME + MFG_LEADTIME);
  if (i & LEADTIME) constrts |= PO_LEADTIME + MFG_LEADTIME;
}
bool isCapacityConstrained() const { return (constrts & CAPACITY) > 0; }
bool isConstrained() const { return constrts > 0; }
```

约束分三类：`CAPACITY`（产能约束，设备/人不能超负载）、`PO_LEADTIME`（采购提前期约束，料不可能在供应商交期之前到）、`MFG_LEADTIME`（制造提前期约束，活不可能在开工之前就干完）。`LEADTIME` 只是个便捷开关，等于后两类提前期一起打开。

这里有个很重要的设计含义：`isLeadTimeConstrained` 的注释写着"solver isn't allowed to create any operation plans in the past"——**约束计划绝不允许把工序排到过去**。今天是 15 号，一张今天就要交的订单按正常提前期本该上周开工，约束模式不会假装你上周已经做了，而是老老实实地把它往后排到最早可行日期，于是这张单被标记为"晚交"。这种诚实，正是 APS 和无限产能 MRP 的根本分野。

但注意一个反直觉的细节，我在 `solveroperation.cpp` 里看到一句很关键的注释：日历上定义的"不可用时间"**即使在无约束计划里也会被检查**，原话是 "also an unconstrained plan can plan demand late!"。也就是说，周日全厂停机这件事，无约束模式也认——它可以无视产能超载，但不会无视"这个时间段物理上关门"。所以"无约束"不等于"无视一切"，别以为选了无约束就能得到一张无视节假日的计划。

## 三种计划类型：同一份数据，三种态度

计划类型的权威定义不在文档、而在 `solver.h` 的注释里，`getPlanType()` 上方那段注释把三种取值讲得一字不差，我把它整理出来：

| planType | 名称 | 满足不了时怎么办 | 需求能否准时足量 |
| --- | --- | --- | --- |
| 1 | 完全约束 Constrained | 不违反任何约束，缺料或缺产能就**晚交或短交** | 可能晚、可能少 |
| 2 | 智能无约束（带替代搜索） | 穷尽替代物料/资源，剩余缺口标在主用项上，**留下问题** | 总是准时足量 |
| 3 | 纯无约束（不找替代） | 直接在主用项上留下物料/产能问题，不评估替代 | 总是准时足量 |

代码里 `setPlanType` 还做了入参校验，超出 1~3 直接抛 `DataException("Invalid plan type")`，默认值是 1。这三种态度分别适合完全不同的决策目的，我用一个"产能只够 80 件、来了 100 件订单、但有台备用机"的例子说明差异：

**planType=1（完全约束，默认）。** 引擎死守所有约束：80 件按交期排上主设备，剩下 20 件它会去尝试备用机；如果备用机也没产能，它绝不在同一天把设备排成 120%，而是把这 20 件排到下一个可行的时间窗——于是这张订单被明确标注会晚交，或者按你设置的规则短交。这张计划是**可以直接下达车间的**，因为它承诺的每一件在时间、物料、产能上都对得上。代价是它不会假装能完成不可能的任务。

**planType=3（纯无约束）。** 这就是经典 MRP 的行为：不管设备当天有没有空，100 件全都按交期倒排进去，产能负载表上那台设备直接冲到 125%，缺的料甚至可能要求"昨天到货"。需求在账面上永远准时足量，但代价是计划里挂满了产能/物料问题（Problem）标记。这种计划不能拿去执行，但它有个不可替代的用途：**回答"如果资源无限，我们到底需要多少料、多少总产能"**——做长期采购需求测算和产能规划时，这正是你要的输入。

**planType=2（智能无约束，最有意思）。** 它在 3 的基础上多做一件事：遇到缺口时，不立刻在主设备上挂个"产能不足"就完事，而是**先把所有替代方案穷尽一遍**——备用机能用吗？替代物料有库存吗？替代供应商能提前吗？把这些都用掉之后，仍然满足不了的那部分，才在主用项上留下缺口问题。例子里它会先用备用机吞掉 20 件里的 15 件，只为主设备报告剩下 5 件的真实缺口。注释特别强调"demand is always fully met on time"（需求始终准时足量），同时把"真正无法弥合的瓶颈"精确地暴露出来。它的价值在中期决策：**当你拿着这份计划去申请买设备、招人、加供应商时，你报告的缺口是穷尽了所有替代后剩下的真缺口，而不是没动脑筋的虚假缺口。**

我个人的使用习惯是三种都跑：用 planType=3 看原始物料需求总量，用 planType=2 跟管理层讲"瓶颈在哪、加多少产能能解决多少问题"，用 planType=1 生成真正下达执行的计划。同一份数据三个视角，决策层次就拉开了。

## 反向排程与正向排程：JIT 与 ASAP

理解了"满足不了怎么办"，再看另一个维度：从哪个时间点开始排。frePPLe 有两个算子——`OperatorBackward`（反向）和 `OperatorForward`（正向），在 `commit()` 一开始就被创建：

```cpp
operator_forward  = new OperatorForward(this, c, mgr);
operator_backward = new OperatorBackward(this, c, mgr);
```

**反向排程（backward，JIT）。** 从需求的交期出发倒推：产品必须在交期那一刻入库，那工序必须在交期减去加工时长的时刻完工，再往前推它该什么时候开工、原材料什么时候必须齐套。这种排程的指导思想是拉动式、准时制——能晚做就晚做，做完正好用上。好处是在制品和原材料库存最低、资金占用最少，和它 README 里标榜的 pull-based planning、lean 完全对应。绝大多数场景默认就是反向，我在 `operatorbackward.cpp` 里看到它只对"被约束的桶状资源"做传播，本质是在维护这套倒排出来的时间关系。

**正向排程（forward，ASAP）。** 反过来，从当前时刻（now）出发，尽早开工、尽早完工。它不追求 JIT，追求最快。纯正向排出来的计划往往偏早、库存偏高，但它在约束模式里有个关键的修复作用：当反向排程算出"这道工序本该上周开工"时（时间已经过去了），反向答案不可执行，这时就需要正向算子把它从"现在"往后推到第一个真正可行的时刻。

## 两次扫描为什么要来回最多五轮

现在可以把第 1 章那段 `commit()` 完全讲通了。约束模式（`heuristic_2` 且 `planType==1`）下，引擎不是只扫一遍，而是：

```cpp
// 第一轮：反向扫描，按 JIT 给每张订单排理想日期
constrainedPlanning = (solver->getPlanType() == 1);
backward_sweep();

if (solver->getPlanType() == 1) {
  short loops = 0;
  while (loops++ <= 5) {
    operator_forward->solve();                    // 正向扫描：把排到过去/撞车的推到可行位置
    if (!operator_forward->getMovedDeliveries())
      break;                                      // 交期没再变动，收敛，结束
    // 删掉除交期单外的试探性工序计划……
    oper.deleteOperationPlans(false, false);
    // 第二轮反向扫描：这次在已经可行的日期上重新协调批量
    setBatchGrouping(true);
    backward_sweep();
  }
}
scanExcess(false);  // 清理多余库存
```

这个"反向→正向→再反向"的循环设计得很妙，逻辑链条是这样的：

1. **先反向**：假设一切理想，给每道工序一个最晚但正好赶上交期的 JIT 日期，这是库存最优解；
2. **再正向**：但很多 JIT 日期在现实里不可行（要上周就开工、或那天设备已满），正向扫描把这些排不下去的交期统一推到最早可行时刻，并记录有多少交期被移动了（`getMovedDeliveries()`）；
3. **删了重排**：交期一旦被推后，原来围绕旧交期排的上下游工序全错位了。于是引擎把试探性的工序计划删掉、只保留交期单，带着这批"已经变可行的新日期"再做一次反向扫描，这次还打开批量合并（`setBatchGrouping(true)`），让相邻订单在可行日期上尽量凑批生产；
4. **迭代到收敛**：一轮下来如果又有交期被推，就再来一轮，直到某一轮正向扫描发现"没有任何交期需要再移动"（`!getMovedDeliveries()`），计划稳定，立即 break。外面套了一个 `loops <= 5` 的硬上限兜底，防止病态数据导致无限迭代。

这个来回迭代体现的是一个深刻的工程现实：**JIT（反向）给的是库存最优的理想解，可行（正向）给的是执行得了的现实解，二者往往冲突，必须反复折中。** 无约束模式根本不需要这一套，因为它允许超载和排到过去，一次反向扫描（`commit()` 里第一个分支 `backward_sweep()` 后直接 `scanExcess`）就算完了——这也从侧面说明，为什么无约束 MRP 跑得快却不可执行：它压根没做这轮现实校验。

需求被逐张处理的顺序也在这个文件里定死了：常规分支在进入循环前先 `stable_sort(demands->begin(), demands->end(), demand_comparison)`，比较规则在头文件注释里写着三级键——先按需求优先级（数字小在前）、再按交期（早的在前）、最后按数量（小的在前）。用稳定排序是为了保证不同平台、不同 STL 实现下结果完全可复现。下一章我们就钻进单张订单内部，看它被排到时发生了什么。

## 怎么选：给三个决策场景的明确建议

- **日常下达车间、给客户做可承诺交期（ATP/CTP）**：用 planType=1 完全约束，产能和两类提前期都打开。你要的是可执行和诚实的晚交预警。
- **评估瓶颈、做中期扩产/招人/拓供应商决策**：用 planType=2 智能无约束。它穷尽替代后留下的缺口，才是值得投钱去填平的真瓶颈。
- **做长周期物料预算和总产能粗算**：用 planType=3 纯无约束（或关闭所有 constraints 的单扫描），看资源无限假设下的总需求。

切换这些模式时配合 `Parameter` 表调参，跑完务必看问题报告（下一章主题）而不是只看甘特图——因为无约束计划的全部价值都挂在那一片红色的 Problem 标记上，只看图你会误以为一切岁月静好。

## 小结

这一章我们把 frePPLe 的计划哲学拆成了三个维度：约束位掩码（产能、采购提前期、制造提前期，且不允许排到过去）决定"考虑什么"；三种 planType（完全约束、智能无约束、纯无约束）决定"满足不了时的态度"；反向 JIT 与正向 ASAP 两个算子决定"从哪个时间点排"。约束模式下"反向给理想、正向修正成现实、再回头协调批量"最多五轮直到收敛，是这份计划可执行的根本原因。
