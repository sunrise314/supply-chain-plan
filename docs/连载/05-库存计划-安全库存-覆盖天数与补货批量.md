# 库存计划：安全库存、覆盖天数与补货批量

预测做完，我们知道了"大概会卖多少"；但预测天生有误差，供应商会迟到，设备会故障。库存计划要回答的就是那个让所有供应链经理睡不着觉的问题：**为了应对这些不确定性，到底该在手里压多少货、什么时候补、一次补多少？** 压多了是占压资金和呆滞，压少了是缺货和违约。这一章我们看 frePPLe 怎么把这个权衡落地。

先建立一个基本认知：frePPLe 的开源引擎在库存这件事上的分工是——**"备多少"这个目标值由你（或外部模型）算好告诉它，"怎么在约束下把库存补到这个目标"由求解器保证。** 它不会在引擎里硬编码一个"服务水平→安全库存"的黑盒公式，但它提供了精确的库存上下限模型、随时间变化的库存曲线，以及一套和排订单共用同一套递归逻辑的补货算法。理解这条边界，你才不会对它产生不切实际的期待。

## 安全库存的统计学根基：它和上一章是连着的

安全库存不是拍脑袋填的一个数，它有清晰的统计学含义。备货的根本原因是不确定性，主要来自两头：需求比预测的高（需求波动），补货比承诺的晚（供给波动）。在最常见的近似模型里，安全库存大致是：

```
安全库存 SS ≈ Z(服务水平) × σ(预测误差) × √(提前期 L)
```

- `Z(服务水平)` 是目标服务水平对应的标准正态分位数：想要 95% 不缺货，Z 约 1.65；想要 99%，Z 约 2.33。服务水平每提高一点，需要砸进去的库存是非线性增长的。
- `σ(预测误差)` 是需求预测误差的标准差。
- `√(L)` 是补货提前期的平方根：提前期越长，期间内可能累积的波动越大，需要的安全库存越多。

现在你应该回头看第 4 章那个 `out_deviation` 字段了——预测跑完回写的"误差标准差"，正是这个公式里的 σ。frePPLe 诚实地把它算出来摆给你，至于要不要套上面的公式、用什么服务水平，由你在库存策略层面决定，算出来的目标下限再写进 Buffer。这种"引擎提供原料、策略由人定夺"的克制，我认为是优点：服务水平是个商业决策（不同物料、不同客户等级本就该不同），不该被软件一刀切。

## Buffer 的库存上下限：下限保命、上限封顶

目标库存落到模型里，就是第 3 章见过的 Buffer 那组字段，这里专门从库存计划的角度讲透：

| 字段 | 含义 | 计划上的作用 |
| --- | --- | --- |
| `onhand` | 当前在手库存 | 计划的起点 |
| `minimum` | 库存下限（安全库存） | 任何时刻库存不应长期跌破的水位 |
| `minimum_calendar` | 随时间变化的下限 | 旺季抬高、淡季压低 |
| `maximum` | 库存上限 | 防止补货把仓库/资金占满 |
| `maximum_calendar` | 随时间变化的上限 | 促销前临时放宽库容 |
| `min_interval` | 最小补货间隔 | 两次补货至少间隔多久 |

下限和上限都能挂日历，这一点前面夸过，这里补一个库存视角的理由：安全库存本就该是季节性的。空调旺季前的 8、9 月，需求波动绝对值大，同样 95% 服务水平对应的安全库存远高于淡季。用 `minimum_calendar` 画一条随月份起伏的下限曲线，比一个全年不变的常数专业得多。而 `maximum` 上限在现实里常常对应仓储容量或资金预算，引擎补货时看到要顶到上限就会收手（代码里对应 `hitMaxEarly` 这类限制）。

## 求解器怎么补安全库存：它就是一次特殊的"需求求解"

最有意思的部分来了：引擎内部并没有为安全库存单独写一套算法。我读 `src/solver/solverbuffer.cpp` 里的 `solveSafetyStock()`，发现它补安全库存的方式，和第 7 章要讲的满足客户订单用的是**同一个 ask-reply 递归**。核心逻辑是这样：

```cpp
void SolverCreate::solveSafetyStock(const Buffer* b, void* v) {
  ...
  // 沿这个 Buffer 的完整库存时间轴扫描整个计划期
  auto cur = b->getFlowPlans().begin();
  while (true) {
    ...
    double theOnHand = prev->getOnhand();
    double theDelta = theOnHand - current_minimum + shortage; // 距下限差多少
    ...
    while (theDelta < -ROUNDING_ERROR && loop && --loopcounter > 0) {
      // 跌破下限：把缺口当成一次"需求"，向补货工序发问
      data->state->curBuffer = const_cast<Buffer*>(b);
      data->state->q_qty = -theDelta;                       // 问的数量=缺口
      data->state->q_date = nextAskDate ? nextAskDate : prev->getDate();
      data->state->q_date -= repeat_early;
      ...
    }
  }
}
```

把它翻译成人话：引擎在时间轴上一格一格走，每个时间点看库存水位 `onhand` 和当时的下限 `current_minimum`；一旦发现库存会跌破下限（`theDelta < 0`），就把"缺的这部分"打包成一次补货请求——`q_qty` 填缺口量、`q_date` 填需要到位的日期——然后向这个 Buffer 的补货工序（`getProducingOperation()`）发问。后面发生的事和补一张客户订单完全一样：补货工序去问产能、问它要消耗的原材料，层层递归。补上来之后库存回到下限以上，继续往后扫。

这个实现里有两个很现实的分支，值得单独说。

**第一，补不了货就明说。** 代码开头先判断 `if (!b->getProducingOperation()) { logger << "Warning: Can't replenish"; break; }`。如果一个 Buffer 根本没有配置补货来源（比如一个外购料忘了维护采购提前期和供应商），引擎不会假装能补，而是打一条 "Can't replenish" 警告，把它暴露成需要人去解决的问题。这种"宁可报错也不静默产出错误计划"的态度，是生产级软件的底线。

**第二，尊重批量上限和补货节奏。** 它会读补货工序的 `SizeMaximum` 限制单次批量，缺口太大就拆成多次补（循环计数 `loopcounter` 还专门做了性能保护，避免极端数据下死循环）；`getMinimumDelay()`/`repeat_early` 这组变量则对应 Buffer 的 `min_interval`——两次补货不能贴得比最小间隔还近，需要提前补时就整体前移。这些约束保证算出来的补货计划是采购和车间真能执行的，而不是数学上正确、操作上荒谬的"每天补一个"。

## 为什么总是"先补安全库存，再排客户订单"

回到第 1 章我贴过的 `commit()` 主循环，常规分支里在逐张订单求解之前，有这么两行：

```cpp
safety_stock_planning = true;
solveSafetyStock(solver, true);   // 先把全网络的安全库存补足
// 之后才进入逐张客户订单的 do-while 循环
```

顺序为什么不能反过来？因为安全库存是一种**不依附于任何具体客户订单的常备需求**，它代表企业对未来不确定性的保底承诺。如果先满足订单、再看还剩多少产能补安全库存，那么一旦产能紧张，安全库存永远会被确定性订单挤掉，名存实亡，等真遇到需求波动就直接缺货。先补安全库存，等于先把"抗波动的缓冲池"填满，再在剩余的物料和产能里排具体订单——这和现实中好的计划员的思路一致：先守住底线，再争取上限。

这里我要诚实指出一个"代码比文档新"的细节。早期版本这个行为是可以通过参数 `plan.planSafetyStockFirst` 关闭的，但我在 execute 应用 2024 年的一个迁移文件里看到，它直接把 `plan.planSafetyStockFirst`、`plan.calendar`、`allowsplits` 三个参数从 `common_parameter` 表里删掉了。也就是说，**当前主线已经取消了这个开关，安全库存固定先算。** 如果你看的是旧版本文档或旧教程，可能还会看到这个参数，以代码为准。

## 覆盖天数：比"库存数量"更直观的健康指标

光看库存绝对数量没法判断健康度——同样 1000 件，对每天卖 500 件的爆款是两天就断货，对一年卖 100 件的慢动销是十年积压。所以更有用的指标是**覆盖天数（period of cover）**：当前库存还能覆盖多少天的需求。Item 模型上那个被标成 `editable=False` 的 `periodofcover` 字段，存的就是计划跑完后回填的这个结果——它不是人填的输入，而是系统结合需求速率算出来的输出。

做库存健康度分析时，我建议直接按覆盖天数把物料分层：覆盖天数远超提前期加安全期的是积压（资金被占用，该促销或减产），低于提前期的是断货风险（该加急补）。这比一刀切的"库存周转率"更早暴露问题，也比死盯数量更符合直觉。

## 一次补多少：批量约束在三处生效

"一次补多少"看似简单，实则要同时满足采购端和生产端的批量规则，frePPLe 把它们分散在三个真实约束里：

- **生产批量**：Operation 上的 `sizeminimum`（最小生产批量，低于不划算开机）、`sizemultiple`（批量倍数，比如必须整托生产）、`sizemaximum`（最大批量，受设备容量限制），`solveSafetyStock` 里正是拿 `getSizeMaximum()` 去拆补货；
- **采购批量**：`ItemSupplier` 上同样有 `sizeminimum`/`sizemultiple`/`sizemaximum`，对应供应商的起订量、包装规格和供货上限；
- **过量清理**：主循环最后那步 `scanExcess(false)` 会扫描多补出来的库存并回收多余计划，避免安全库存逻辑和订单逻辑叠加后产生呆滞。

这三者合起来，回答了库存领域经典的 lot sizing 问题：既不为零头频繁开机/下单（被最小批量和最小间隔拦住），也不一次补到爆仓（被最大批量和上限拦住）。至于"凑大批量省换型/省运费"的并批优化，则由 Operation 的 `batchwindow` 时间窗参数控制——引擎会在需求日前后的窗口内主动寻找能合并的批次。

## 落地建议：怎么给 frePPLe 喂安全库存目标

开源版不会替你决定服务水平，那实践中目标从哪来？我会这样做：

1. 先跑一轮第 4 章的预测，拿到每个物料的 `out_deviation`（误差标准差）和 `out_smape`；
2. 按物料的重要性分级（A/B/C 类），给不同等级设不同目标服务水平，A 类 98%、C 类 90% 甚至更低——给螺丝和给核心部件同样 99% 服务水平是对资金的浪费；
3. 用前面的公式结合采购提前期算出每个 Buffer 的 `minimum`，季节性强的物料改填 `minimum_calendar`；
4. 这些目标通过 Excel/CSV 或 REST 批量导入，`AuditModel.source` 字段标注来源（比如标成 "safety-stock-v1"），方便日后追溯和重算；
5. 跑计划后用覆盖天数报表回看实际效果，迭代校准服务水平和标准差。

## 小结

这一章我们看到，frePPLe 把库存计划拆成了两层：策略层由你依据预测误差（`out_deviation`）、服务水平（Z 值）和提前期（√L）决定安全库存目标，写进 Buffer 的 `minimum`/`minimum_calendar`，并用 maximum 和 min_interval 划好边界；执行层则由 `solveSafetyStock()` 沿库存时间轴扫描，把每个跌破下限的缺口当成一次特殊需求，复用产能/物料的 ask-reply 递归去补货，同时尊重生产/采购批量和补货节奏。安全库存永远先于客户订单被满足，过量库存最后被 `scanExcess` 清理。
