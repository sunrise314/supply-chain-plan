# 核心求解器：ask-reply 递归怎么把一张订单展开成计划

这是整个系列最硬核的一章。前面六章我们搭好了网络、备好了料、选好了计划模式，但求解器内部到底是怎么"想"的，一直是个黑盒。这一章我带你钻进 frePPLe 的 C++ 引擎，逐行看清它最核心的机制——ask-reply（请求-应答）递归。理解了它，你就理解了为什么一张销售订单进去，能吐出一张跨越整个 BOM、精确到分钟、包含采购/生产/调拨全部单据的计划。

## 一个统一的对话协议：ask 和 reply

整个求解器建立在一个极其简单的对话协议上。计划网络里的每一个对象——一道工序、一个库存点 Buffer、一台资源 Resource——都可以被"问"，也都要"答"：

- **请求 ask** 是一个二元组 `(q_qty, q_date)`：我在 q_date 这个时间点，需要 q_qty 这么多；
- **应答 reply** 也是一个二元组 `(a_qty, a_date)`：我能在 a_date 这个时间点，给你 a_qty 这么多。

应答遵循两条铁律。其一，**绝不给得比要的多**，我在代码里直接看到注释 "Never answer more than asked"，所以 `a_qty` 永远不超过 `q_qty`。其二，给不了就答 0、给得晚就改日期：`a_qty = 0` 表示彻底无法满足，`a_date` 被推后则表示"东西有，但要晚一点"。求解器在 `checkOperation()` 里给应答设的默认值，把这种乐观假设暴露得很明白：

```cpp
bool SolverCreate::checkOperation(OperationPlan* opplan, SolverData& data, ...) {
  // 默认应答：假设你要的量我全都能给、时间无限靠后（先乐观，再逐步被现实修正）
  data.state->a_date = Date::infiniteFuture;
  data.state->a_qty = data.state->q_qty;
  ...
}
```

整个求解过程，就是这个 `(q_qty, q_date) → (a_qty, a_date)` 的问答在网络里一层层向下传、再一层层把结果向上冒泡的过程。

## 入口：需求排序后逐张求解

故事从 `solverdemand.cpp` 开始。第 6 章讲过，所有需求先由 `demand_comparison` 做稳定排序，三级键是优先级（小的在前）→ 交期（早的在前）→ 数量（小的在前）。然后求解器遍历这个有序列表，每一张需求还要过一遍资格检查：只有 open/quote 状态、有未满足数量、交期不是无限远的才处理。代码里反复出现的判断就是这个意思。

对一张被选中的需求，引擎先为它创建一个交付工序计划（delivery operationplan），交期 = 需求的 due 减去一个行政提前期。接着它就拿着第一个请求去问这道交付工序：**"在交期那天，给我这张订单的成品。"** 递归从这里启动。

## 工序被问之后：它要同时去问产能和物料

一道工序收到"生产 X 个、某时点交货"的请求后，不能凭空答应，因为它有两类依赖要确认：**用哪些资源（产能）、消耗哪些物料（料）**。它的做法是分别去问这两边。

先看产能这一侧。`solveroperation.cpp` 里有一段遍历所有负载计划（loadplan）的循环，每遇到一个资源占用就构造请求、调用负载求解器（它内部再调资源求解器）：

```cpp
for (auto h = opplan->beginLoadPlans(); h != opplan->endLoadPlans(); ++h) {
  ...
  // 构造给资源的请求：要多少产能、什么时间
  data.state->q_operationplan = opplan;
  data.state->q_loadplan = &*h;
  data.state->q_qty = h->getQuantity();
  data.state->q_date = h->getDate();
  h->getLoad()->solve(*this, &data);   // 负载求解器 → 资源求解器
  ...
}
```

资源求解器拿到请求后，会在资源日历上找空闲产能，考虑最大负荷、效率、换型矩阵（SetupMatrix）、以及同名 Load 定义的替代资源池（按 priority/search 选）。找到就答"能给"，并可能把工序整体前后移动到有空档的时间；找不到就答 0。

物料这一侧对称。`solverflow.cpp` 里，工序对每条物料流（Flow）构造请求，然后**直接问对应的 Buffer**：

```cpp
data->state->q_flowplan->getBuffer()->solve(*this, data);
```

Buffer 求解器会沿着这个库存点的库存时间轴（FlowPlan timeline）检查：在请求的那个时间点，投影库存（现有库存 + 在此之前已经确定的入库 − 已分配的出库）够不够。够，立即给一个肯定应答，递归在此终止；不够，事情就变得有趣了——Buffer 会转而**去问它的补货工序**。

## 递归：缺口沿 BOM 向下传

这就是整个算法最精妙的递归环节。Buffer 自己不生产东西，它发现库存不足时，会找到"为这个库存点补货的工序"（`getProducingOperation()`，第 5 章补安全库存时见过同一个调用），向那道工序发出一个新请求："我在某时点缺这么多，你给我补。"而那道工序为了补这个料，又要去问它自己的资源和它消耗的更底层物料 Buffer；底层 Buffer 不够，再问更底层的工序……

我在 `solverflow.cpp` 里看到，连替代物料都走同一个递归——首选料 Buffer 答不了时，它会取同名替代组里的下一个：

```cpp
data.state->q_date = flplan->getDate();
firstAlternate->getBuffer()->solve(*this, data);  // 换替代物料的 Buffer 再问一次
data.state->a_qty = -flplan->getQuantity();
```

于是，一次"要成品"的顶层请求，就沿着负物料流（model.h 里 `quantity < 0` 即消耗）层层向下分叉，形成一棵请求树。成品装配问零件，零件加工问原材料，原材料是外购的，就走到叶子——由 ItemSupplier 的采购提前期决定应答日期，不再继续向下。**这棵请求树的深度，恰好就是 BOM 的层数**，这也是为什么第 3 章我说"BOM 多层展开不需要单独的 MRP 程序"——展开是递归的自然结果。

递归有三种终止（base case）：
1. **库存足够**：Buffer 检查时间轴发现够，立即肯定应答，不再向下；
2. **排到过去**：约束模式下，如果要满足请求必须在"现在"之前就开工，立即否定应答——时间不能倒流；
3. **到达外购叶子**：没有补货工序的 Buffer，按供应商提前期给一个现实日期，或者在彻底没有供货来源时打 "Can't replenish" 警告。

## 应答冒泡：0、晚交与多资源重检

请求向下传的时候，应答要一层层往上冒泡，这里有几个很见功力的处理。

**答 0 的传播。** 如果某个资源彻底没戏，它的应答是 `a_qty=0`、`a_date=infiniteFuture`。工序收到这种应答，代码注释直接写着 "Game over"，会把工序计划数量清零并立即返回：

```cpp
if (data.state->a_qty == 0) {
  if (data.state->a_date == Date::infiniteFuture) {
    // Game over
    if (opplan->getQuantity() > 0.0) opplan->setQuantity(0.0);
    return;
  }
  // 资源只是会晚，不是彻底不行：后续只能推迟，防止别的资源又把它往前拉
  data.state->forceLate = true;
  delayed_reply = true;
}
```

而一旦被迫晚交（`delayed_reply` 或 `forceLate`），应答量也会被强制清零（"A late reply was forced, which always means a reply of 0"），并立刻把这个工序计划 resize 成 0。注释解释了原因：必须让上游 Buffer 的库存曲线也尊重这个答案，否则库存账会以为这批货还能按时到。

**多资源的重检循环。** 一道工序可能同时占好几个资源（一台机器 + 两个工人）。检查工人时工序被推迟了，那原本确认有空的机器在新时间点未必还空。所以代码在一个 `do-while` 里反复重检所有负载——只要任一负载移动了工序日期，就得回头重新确认之前查过的资源，直到没有负载再改动日期、或被证明不可行。这个循环外面同样套了硬上限（`counter >= 20` 就退出），防止极端数据下死循环，源码里还留了一句自我怀疑的 TODO（担心 a_penalty 累加是否正确）。这类细节让我确信它是在真实生产数据里磨出来的。

## 试探与回滚：用书签实现"试错不污染"

递归求解天然要试错：问 A 替代不行就回退问 B，某个日期排不下就往后挪。可试的过程中已经往库存时间轴上插了一堆试探性的工序计划，失败了怎么干净地撤销？答案是一个命令管理器（CommandManager）加书签机制。我在 `solverflow.cpp` 发问前看到：

```cpp
auto topcommand = data->getCommandManager()->setBookmark();
data->state->q_flowplan->getBuffer()->solve(*this, data);
```

在发起一次试探性递归前先打个书签（setBookmark），递归过程中产生的所有增量改动都由命令管理器记录；如果回来的应答不能接受（量不够或太晚），就回滚到这个书签，撤销这次试探插入的全部工序计划，然后换一个替代项或下一个日期重新发问。这套"建立检查点 → 试探 → 不满意就整体回滚"的机制，对应的正是 `operatordelete.cpp` 那一类负责删除/撤销工序计划的算子。它让引擎可以大胆地在解空间里探索，而不用担心半成品计划污染库存和产能账目。第 6 章讲约束模式下"删掉试探计划、重新反向扫描"，底层依赖的也是同一套命令回滚能力。

## 跟一张订单走一遍：具象的递归

我们用第 3 章那个机械加工厂的例子，把整个过程走一遍。客户下单一台成品泵，交期 11 月 20 日。

1. solverdemand 按优先级和交期轮到这张单，建交付工序，发出顶层 ask `(1 台, 11-20)`；
2. 装配工序收到，先问**资源**：总装工位 20 号前有连续 4 小时空档吗？有，暂记；
3. 再问**物料**：泵体 Buffer、电机 Buffer、螺栓 Buffer 各有料吗？泵体现有 0，Buffer 向"泵体加工"工序发出 ask `(1 件, 装配开工日)`；
4. 泵体加工工序又问它的数控车床（产能）和铸件 Buffer（料）：车床有空，但铸件不够，铸件 Buffer 转向"铸造工序"，铸造再问生铁 Buffer 和熔炼炉……递归继续向下；
5. 生铁是外购件，到达递归叶子，ItemSupplier 应答：采购提前期 15 天、最小起订 100 件，最早 11 月 5 日到货；
6. 应答开始冒泡：铸造工序据生铁到货日 + 熔炼 + 冷却时长，回出铸件可行日期；泵体加工据铸件日期 + 车床空档，回出泵体可行日期；装配据所有零件里最晚到位的那个（瓶颈物料）+ 总装工位空档，回出最终完工日；
7. 如果最终完工日 ≤ 11-20，顶层应答成功，订单准时；如果某一环（比如车床在窗口期根本排不进）回了 0 或晚交，引擎会先用命令回滚，尝试同名替代资源/替代物料（planType=2 时穷尽替代），仍不行就按计划类型决定：约束模式标晚交/短交，无约束模式让订单账面准时、但在车床上挂一个产能问题。

每一步 ask 都带着量和日期，每一步 reply 都只回答"能给多少、什么时候"，没有中央大脑做全局通盘计算，复杂的全局计划就这样从局部的、成对的问答中涌现出来。

## 为什么用启发式递归，而不是求全局最优

懂运筹学的读者可能会问：这不是贪心吗？逐张订单、局部应答，为什么不用线性规划/混合整数规划（LP/MIP）求全局最优？frePPLe 选择启发式（heuristic，README 和算法名 `heuristic_2` 都不讳言）是有道理的：

- **规模**：真实供应链几万张订单、几万 SKU、多层 BOM，精确 MIP 模型可能几小时都不收敛，而计划员需要分钟级出结果；启发式逐需求求解，复杂度可控。
- **可解释**：每张订单为什么晚、卡在哪个资源或缺哪种料，可以沿 ask-reply 的调用链一步步追出来（下一章的 pegging 就是干这个）；MIP 给你一个最优解，但很难解释"为什么"。
- **贴合实际决策**：现实计划本就有优先级（重要客户先满足）、本就是逐单承诺的，priority→due 的贪心顺序正好模拟了计划员的真实工作方式。

代价是它不保证数学最优，极端情况下早排的低优先级订单可能占了资源、导致后面高优先级订单受损（虽然排序已尽量规避）。这是一个明确的工程取舍：**用可接受的次优，换速度、可扩展和可解释。** 如果你有少数关键瓶颈工序需要严格最优排程，frePPLe 的定位是把它当成整体供应链的协同层，瓶颈局部可以接更强的优化器（比如第 1 章提的 Timefold），这也是 polyglot 架构的用武之地。

想看这个递归的实时过程，把参数 `plan.loglevel` 设成 2 再跑计划，日志里会打出形如 "OperationPlan '...' is asked: &lt;q_qty&gt; &lt;q_date&gt;" 的完整问答轨迹，是理解算法最好的教具。

## 小结

这一章我们看清了 frePPLe 的求解内核：一个 `(q_qty,q_date)→(a_qty,a_date)` 的统一问答协议；需求按优先级/交期/数量稳定排序后逐张进入；每道工序分别向资源问产能、向 Buffer 问物料，Buffer 不足就转而向补货工序发问，递归沿 BOM 下行、深度恰为 BOM 层数，在库存足够、必须排到过去、外购叶子三种情况下终止；应答层层冒泡，0 和晚交有严格的传播规则，多资源相互牵连时反复重检；命令管理器的书签让所有试探可整体回滚。它是一套追求速度与可解释的启发式贪心，而非全局最优。

但算出来只是第一步。计划员真正关心的是：这张订单到底为什么晚？缺的料影响了哪些单？下一章我们讲 frePPLe 怎么用问题（Problem）标记和供需追溯（pegging）把这张计划变成一份能拿去开会、能追责、能做决策的诊断报告。
