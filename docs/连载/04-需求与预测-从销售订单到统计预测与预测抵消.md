# 需求与预测：从销售订单到统计预测，再到预测抵消

供给网络搭好之后，系统已经"知道产品怎么造"了。但它还不知道"该造多少、什么时候要"。这一章我们走到决策链最上游，看需求从哪来。frePPLe 里需求有两个来源：已经落下来的**销售订单**，和还没落地、需要靠历史猜的**预测**。前者确定但来得太晚（等下单再生产往往赶不上交期），后者提前但天生不准。一个靠谱的计划系统要把两者结合起来用，这就是本章的主线。

## Demand：一张订单要满足什么

先看确定性需求。Demand（表名 `demand`）继承 `AuditModel`，它的外键结构一眼就说明了"需求"这件事的三要素：`item`（要什么）、`location`（交到哪）、`customer`（卖给谁），三者都建了索引。除此之外关键字段还有：

- `due`：交期，带索引的日期时间，整个排程围绕它倒推；
- `quantity` 和已计划量：引擎要保证不超计划、不重复计划；
- `priority`：优先级，数字越小越重要——第 7 章你会看到，逐需求求解时排序的第一关键字就是它；
- `status`：订单状态；
- `operation`：指定用哪道交付工序来满足这张订单，为空则由系统自己找。

`status` 上有个必须强调的业务规则。我在求解器源码里反复看到这样的判断条件：

```cpp
if (salesorder->getQuantity() - salesorder->getPlannedQuantity() > ROUNDING_ERROR &&
    salesorder->getDue() < Date::infiniteFuture &&
    (m->getStatus() == Demand::STATUS_OPEN ||
     m->getStatus() == Demand::STATUS_QUOTE || ...))
```

也就是说，**只有 open（已确认）和 quote（报价中）状态、且还有未满足数量、且交期不是"无限远"的需求，才会被排进计划。** inquiry（询价）阶段的线索只是个意向，不该消耗产能和物料。这个区分看似小事，但很多排程系统把询价单也算进需求，凭空造出一堆永远不会发生的计划——frePPLe 在入口就把它挡掉了。

Demand 上还有两个很实用的服务字段：`minshipment`（最小发货量，不足不排）和 `maxlateness`（最多允许晚多久，超过就直接判为无法满足而不是无限往后拖）。它们让"可接受的现实"和"理想化的数学解"之间有了协商空间。

## Forecast：把预测也当成一种"需求"

frePPLe 一个很顺的设计是：预测在系统里也是一张需求表 `forecast`，同样以 `item + location + customer` 三元组为唯一键（`unique_together`），同样有 priority、minshipment、maxlateness、discrete、planned 这些计划属性，还同样挂了一个交付 `operation` 外键。换句话说，**对求解器而言，一张预测单和一张销售订单没本质区别，都是"某个时间点需要一定数量的某物料"。** 区别只在于预测单的数量是算法估出来的。

预测方法在模型里是一个 `method` 枚举，默认 `automatic`，可选项有八个：automatic（自动）、constant（常数）、trend（趋势）、seasonal（季节性）、intermittent（间歇性）、moving average（移动平均）、manual（人工）、aggregate（聚合）。跑完一次预测后，结果会回写到三个 `out_` 开头的字段里，这个设计我特别欣赏，因为它把"黑盒预测"变得可审计：

- `out_method`：自动模式下最终实际选用了哪种方法；
- `out_smape`：该方法的预估误差（SMAPE 百分比）；
- `out_deviation`：预测误差的标准差。

记住 `out_deviation`，它不是个摆设——下一章讲安全库存时，"到底备多少安全库存"在统计上正是由需求波动（这个标准差）和目标服务水平共同决定的。预测和库存两章在这个字段上接上了头。另外 `discrete`（默认 True）会把预测数量取整成整数，`batch` 字段则用于 MTO 批次命名。

## 自动选方法：不是拍脑袋选一个模型，而是回测择优

`automatic` 到底怎么自动？我去读了 C++ 侧的预测引擎 `src/forecast/timeseries.cpp`，它的做法比"无脑套一个模型"严谨得多，分两步。

**第一步是资格筛选。** 引擎实例化了一组算法对象——移动平均、Croston（克斯顿法，专门对付间歇需求）、一次/二次指数平滑（二次指数平滑就是 Holt 法，能捕捉趋势）、季节性模型、人工等，用一个最多 6 个槽位的 `qualifiedmethods[]` 数组装"本次有资格上场的方法"。资格规则写得很接地气：

```cpp
if (historycount 太少)
    // 历史太短，只敢用移动平均或强制方法
if (zero > Croston::getMinIntermittence() * historycount)
    // 零值占比太高（典型的备件、慢动销）：用 Croston 或移动平均
```

这背后是统计学常识：只有十几个历史数据点，你去拟合季节性模型纯属过拟合；而像备件那种"半年不卖一件、一卖就要命"的间歇需求，用普通平均法会严重虚高，得用 Croston 这种把"需求发生率"和"需求量"分开建模的方法。**先按数据形态排除注定不靠谱的方法**，这一步就比很多"all in 一个模型"的系统成熟。

**第二步是在合格方法里用历史回测比误差，选最小的。** 误差指标用 SMAPE（对称平均绝对百分比误差），而且近期数据权重更高——引擎初始化了一个权重数组，`weight[i+1] = weight[i] * Forecast_SmapeAlfa`，衰减系数 `SmapeAlfa` 默认 0.95。这意味着最近一期的预测偏差比一年前的偏差更能决定模型选型，符合"市场在变、近期更有参考价值"的直觉。选出的方法名和它的 SMAPE 就写进前面说的 `out_method`、`out_smape`。

## 离群点与呆滞料：预测前先清洗

真实销售历史里全是噪声，直接拿去拟合一定翻车。引擎在拟合前做了两类我很认同的清洗。

**离群点剔除。** 每次预测开头先删掉旧的 `ProblemOutlier` 问题标记（`deleteOutliers`），重新用一个阈值 `Forecast_maxDeviation`（默认 4.0）识别异常销量。一笔远超正常波动的偶发大单（比如一次性的工程样机订单）不应被当成"未来都会这么卖"，识别出来后剔除或降权，避免把预测整体抬高。注意它用的是"问题（Problem）"机制而不是悄悄删数据——异常仍然被标记、可追溯，只是不污染拟合。

**呆滞料停测。** 引擎里有个 `DeadAfterInactivity`（停用阈值）的逻辑：如果一个物料在足够长的时间里完全没有任何需求，就认为它已经进入生命周期末期，不再持续预测、释放算力。对动辄几万 SKU 的企业来说，不给死掉的物料算预测，是实打实的性能优化，也避免库存计划被僵尸物料干扰。

## 层级预测：middle-out 与两个维度

实际企业很少在"单个 SKU + 单个仓 + 单个客户"这种最细颗粒度上直接做预测——最细层数据太稀疏、噪声太大；在最顶层（全公司总量）做预测又准但没法落地。frePPLe 的解法是**沿层级做 middle-out（中间出法）预测**。

预测求解器里有个参数 `Customer_Then_Item_Hierarchy`（默认 true），说明它在两个维度上都建了层级：先客户层级（大区→客户组→客户）、再物料层级（产品族→产品→SKU），正是第 2 章那套 `HierarchyModel` 嵌套集在这里的用武之地。代码注释明确写着 "Time series forecasting for all middle-out parent forecasts"——在颗粒度适中的中间层（比如某个产品族、某个客户组）跑统计预测，因为这一层数据量够大、规律性最强，再把结果向下拆解（disaggregate）到叶子 SKU。当一个叶子节点自己的历史太少、不够支撑任何方法时，还可以直接用 `aggregate` 方法，由上层聚合预测分摊下来。这比在最细层硬算准得多，是工业界做层级预测的标准姿势。

## 预测抵消（netting）：别把"预测了的"和"已下单的"重复算两遍

这是本章最关键、也是最容易被忽略的一个环节。假设系统预测 10 月卖 1000 件，到了 10 月真有客户下了一张 300 件的订单。这时候总需求是 1000 还是 1300？答案是 **1000**——那张订单里有 300 件已经被预测覆盖了，不能既算预测又算订单，否则重复备货 300 件。用订单去冲抵同期毛预测的过程，就叫**预测抵消（forecast netting / consumption）**。

我在预测求解器里看到了对应的实现痕迹：`while netting demand ...` 的处理段，以及两个核心度量 `forecastconsumed`（已被订单消耗的预测量）和 `forecastnet`（抵消后的净预测）。抵消时同样调用了 `disaggregate`——因为订单往往落在叶子层，而预测可能做在中间层，需要把"已消耗量"沿层级一致地拆解、回滚上去，保证各层账目对得平。抵消之后真正喂给后续主生产计划的，是净预测 `forecastnet` 加上尚未被预测覆盖的订单增量。

我用一个跨月的小例子把账目算具体：10 月毛预测 1000 件，当月已下订单 300 件，于是 forecastconsumed=300、forecastnet=700，系统按 700 件去备料；到 11 月一张订单都还没来，净预测就是完整的 1000 件，照常备货。订单超过毛预测的情况也成立：如果 10 月实下了 1200 件订单，订单把 1000 件预测全部抵消后还多出 200 件，这 200 件会作为净增量直接进入计划，系统不会因为"预测只有 1000"就无视这多出来的真实需求。这三条规则合起来，保证了既不重复备货、也不漏掉超出预期的真订单。

这里有个工程上的微妙之处值得一提：毛预测、已消耗、净预测三者都是"度量（measure）"而不是写死的列。frePPLe 的预测编辑器本质是一张可以自定义度量的表——你可以叠加人工调整量、促销增量、管理修正等多个度量，最后组合出用于排程的需求。这给了计划员"算法给基准、人来拍板修正"的空间，也是为什么它的界面叫 forecast editor 而不是 forecast report。

## 一个诚实的补充：AI 预测还只是 beta

这两年大模型和机器学习预测被吹得很神，我特意去看了 frePPLe 这方面的成色。仓库里确实有个 `mlforecast` 应用，`__init__.py` 里写得很坦诚：它基于 Uber 的 Orbit 库做机器学习预测生成，**"still in beta-testing and would require the frePPLe team to help to make it production ready"**——还在 beta，要做到生产可用需要官方团队协助。

我的态度和这个注释一致：对绝大多数企业，前面那套"回测择优 + 离群点清洗 + 层级 middle-out + 净预测"的统计方法，已经能把预测准确度做到远胜 Excel 的水平，而且可解释、可审计、零额外依赖；机器学习预测在数据量足够大、外部变量足够多时才有明显增益，且需要专人调优和治理。别一上来就迷信 AI，先把统计基线用好。

## 小结

这一章我们理清了需求的两条腿：确定性的销售订单（只有 open/quote 才进计划）和算法生成的预测（在求解器眼里也是一种需求）。预测引擎用"资格筛选 + SMAPE 回测择优"自动选模型，用离群点剔除和呆滞停测清洗历史，用 middle-out 在客户和物料两个层级上做聚合拆解，最后用订单抵消毛预测得到净预测，还顺手用 `out_deviation` 给下一章的安全库存备好了原料。
