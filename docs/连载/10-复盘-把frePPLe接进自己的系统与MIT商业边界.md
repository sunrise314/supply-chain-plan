# 复盘：把 frePPLe 接进自己的系统，以及 MIT 协议下的商业边界

九章下来，我们从最上游的需求预测一路走到了多仓分销和场景沙盘。收官这一章，我不谈某个具体算法，谈三个真正决定它能不能在你手里产生价值的落地问题：**怎么把它接进你现有的系统、怎么把它部署得稳、以及在开源协议的边界下一个团队该怎么合法又划算地用它。** 最后我会把它和我主语言 Java 生态里的 Timefold 摆在一起，给出我自己的分工建议。

## 定位先摆正：frePPLe 是计划引擎，不是主数据的主人

动手集成前，定位必须摆正。frePPLe 官方架构文档里专门讲了一种用法：把它当成**没有用户界面的后台计划引擎**（backend planning engine without user interface）嵌进别的系统，用户继续用原来的系统当前端，frePPLe 在后台算计划。这句话决定了集成的基本姿态——**你的 ERP/MES/OMS 仍然是主数据的主人（system of record），frePPLe 是计划的主人（system of planning）。** 物料、客户、真实订单在 ERP 里维护，定期同步给 frePPLe；它算完，把建议的采购单、工单、调拨单再推回 ERP 走审批和执行。别试图让 frePPLe 反向接管你的主数据，那是以短攻长。

想清楚定位后会发现，它为此准备了四条数据通道，由浅入深你可以按团队情况选。

## 通道一：REST API（最适合系统对接）

frePPLe 用 Django REST Framework 搭了一套覆盖所有实体的 REST API。我在代码里看到，各应用把序列化器统一注册到一个 `rest_api_router`：`input/urls.py` 里连续 `register` 了 item、buffer、operation、demand 等几乎所有主数据实体，根 `urls.py` 里 `urlpatterns += rest_api_router.urls`，统一挂在 `/api/` 前缀下，还带了一个 `/api/` 的索引页和 `/api-auth/` 认证。

两个工程细节值得说。其一，依赖里有个 `django-bulk-drf`，意味着这些接口支持**批量 upsert**——你可以一次 POST 上千条物料或订单，而不是逐条发请求，这对全量同步至关重要。其二，鉴权用 Token，仓库里有个 `generatetoken` 管理命令专门给集成账号生成长期令牌。典型的对接流程是：ERP 侧定时用 Token 调 `/api/input/demand/` 推送增量订单（第 2 章那个 `source` 字段正好标数据来源、`lastmodified` 支持增量），然后调用执行接口触发计划。

触发计划本身也是一个 API：execute 应用注册了 `^execute/api/(.+)/$` 的任务接口。你 POST 一个"生成计划"的任务，它不会让你的 HTTP 请求干等几分钟——这就要说到它的 worker 机制。

## 长任务 worker：别在 Web 进程里等计划算完

execute 应用的 `Task` 模型里有个 `submitTask()` 静态方法，注释一句话点破了设计："Check if a worker is present. If not launch one."（检查 worker 在不在，不在就启动一个）。架构文档也明确把跑计划、数据库备份、场景复制列为由独立 worker 进程执行的长任务。webservice 应用里那对 `PingService`/`StopService`（ASGI）就是 Web 进程和 worker 之间的心跳与控制通道。

完整链路是这样：你的系统 POST 一个任务 → 立即拿到任务 id → 没有活跃 worker 就拉起一个 → worker 在独立进程里调用 C++ 引擎算 → 状态写回 Task 表 → 你的系统轮询任务状态或 ping 接口，完成后再去 `/api/` 拉取 operationplan 结果。**集成时务必按这个异步模型设计，千万不要用一个同步 HTTP 长请求等计划跑完**，否则就是在重演"慢任务拖垮网站"的事故。这点和我们做 Java 系统时把重活丢给线程池/消息队列、前端轮询任务状态是一模一样的思路。

## 通道二：CSV / Excel（最简单、最稳的批量通道）

如果你的 ERP 比较老、开放不出干净的 API，别硬做接口。frePPLe 的 `input/commands/load.py` 提供了一个很成熟的命令行导入器（配套 `export.py` 导出），用 `frepplectl.py` 就能把 CSV/Excel 灌进任意实体表。这其实是很多老牌计划团队最信赖的方式：ERP 每天凌晨导出一批固定格式的扁平文件（物料主数据、库存快照、未结订单、在途采购），丢到约定目录，frePPLe 定时 load 进来、跑计划、再 export 出建议单据。

第 2 章讲过它用字符串业务键做主键，这个设计在文件集成时优势巨大：CSV 里的物料编码、单号就是主键，重复导入天然是幂等的 upsert，不会像自增 id 那样因为导入批次不同而错位。对绝大多数中小工厂，**"定时文件 + 命令行"这套朴素方案的可靠性和排障便利性，甚至强过硬凑的实时 API**，出问题时你拿一个 Excel 就能复现。

## 通道三：直连数据库（强大但要克制）

官方明确说 schema "simple and stable"，并且**允许外部应用直接在数据库层面集成**。你可以让 ETL 程序直接往 PostgreSQL 里写数、从结果表读数，性能最高、最灵活。但我要泼一点冷水：直连库意味着你绕过了模型层的校验——第 3 章那些 `save()` 里的领域规则（routing 子工序必须是叶子、alternate 不能嵌套、层级不能成环）你都得自己保证。我的建议是：**读结果、做报表可以放心直连（只读最安全）；写主数据优先走 API 或 load 命令，让它替你兜校验。** 真要直连写入，就只写最规范的那几张输入表，并在导入后跑一次数据校验。

## 通道四：现成连接器（Odoo 及通用 ERP）

如果你的后端是 Odoo，省事了——仓库里有个完整的 `odoo` 应用（models/views/urls/commands/utils 齐全），能双向同步产品、客户、销售订单、采购单。此外还有个 `erpconnection` 通用应用预留了 ERP 对接的扩展点。这些连接器展示了官方推荐的集成骨架，哪怕你接的是别的 ERP（比如用友、金蝶或自研系统），照着它的同步粒度和字段映射改，也比从零设计快。

## 部署：别在本机手搓 C++23

部署这块我在第 1 章打过预防针，这里给可执行的建议。核心组件就三样：一个 PostgreSQL（唯一生产库）、一个 Python 3.12 虚拟环境（装 requirements.txt 里的 Django/DRF/psycopg2 等）、一个 C++23 编译出的引擎内核。最容易劝退人的是 C++23 工具链——gcc 14+/clang 18+，本机版本不对会卡在编译上。

正确姿势按难度排：**本地开发直接用仓库自带的 `.devcontainer`**（里面配好了 Dockerfile 和 docker-compose，VS Code 一键进去，工具链全齐），或用 `contrib/docker/ubuntu-24.04.dockerfile` 那套官方镜像构建；**服务器部署用 Docker Compose**（`contrib/docker/docker-compose.yml.in`）或官方 Ubuntu 24.04 安装包，官方文档 `installation-guide/docker-container.rst` 有完整步骤。只有你要改 C++ 求解器时，才需要真正关心编译器。配置集中在 `djangosettings.py` 加数据库里的 `common_parameter` 键值表——还记得吗，改某些参数会自动同步到所有在用场景并触发 worker 重载，调参优先改 Parameter 而不是改代码。

两个运维小抄：数据库备份是 worker 长任务，别在请求里做；另外仓库里有个 `archive` 应用，专门处理历史计划数据的归档，和我在 TMS 里做的轨迹冷热分离是同一类考量——operationplan 会无限增长，定期归档旧数据能保证长期跑计划的性能。

## 协议：MIT 很自由，但版本和企业版边界要看清

这个话题我在第 1 章就立了"诚实讲清"的 flag，这里给出可落地的结论。

**当前主线是 MIT 授权。** 根目录 `COPYING` 写明双授权、可免费按 MIT 使用，我翻的源文件头（从 2007 年的 item.py 到 2026 年新写的 operatorbackward.cpp、2024 年的迁移脚本、2023 年的 mlforecast）都是标准 MIT 全文。MIT 允许你商用、修改、私有化部署甚至再授权，唯一硬性义务是**保留版权声明和许可文本**。你把它二开后做成公司内部系统、或打包进对外交付的解决方案，都没有 AGPL 那种"必须开源你自己代码"的传染性——这对商业交付是决定性的友好。

**但有三个边界必须看清：**

1. **版本陷阱**：早期 6.x 代社区版曾是 AGPL v3。务必从官方渠道拉新版本（当前代码已到 10.0.0 开发态、稳定包 9.x），并在交付清单里锁死版本号和对应的协议文本。别从来历不明的旧镜像下载，否则可能拿到 AGPL 版本。
2. **企业版功能不在 MIT 仓库里**：frePPLe bv 售卖的商业版包含一些开源仓库没有的东西，比如面向分销供应链的第二个求解器、部分高级连接器；`mlforecast` 那个基于 Orbit 的机器学习预测也还在 beta，官方明说生产化需要他们协助。你不能拿 MIT 仓库里不存在的企业功能去承诺客户。
3. **免责与署名**：MIT 软件按"现状"提供、无担保，出问题作者不担责；再分发时保留版权头，别把 frePPLe 的署名抹掉冒充完全自研。

简单说：**用开源核心做内部系统和一般商业解决方案，MIT 下完全自由；要卖"官方增强能力"或需要 SLA 支持，那是商业授权的事。** 真要做严肃商业产品，上线前让法务花半小时过一遍版本和协议，成本极低。

## Java 视角：frePPLe 和 Timefold 怎么分工

作为 Java 工程师，最后必须回答"它和 Timefold 怎么选"。我在第 1 章排除了用 Timefold 做这张卡片，但它在真实架构里有清晰的位置。我的结论是：**两者不是替代，是不同层级，可以协同。**

- **frePPLe 适合做端到端的供应链协同层**：需求预测、安全库存、采购、多仓分销、多层 BOM 的有限产能主计划，它全都有现成的实体模型、算法、界面和结果单据。你要的是"一张覆盖全链路、可执行、可诊断的计划"，用它。
- **Timefold 适合做某个局部的纯 Java 优化内核**：当你有一个边界清晰、约束复杂、需要追求近优解的排程子问题（比如一个车间的机台排序、一个仓的拣选路径、车辆配载），想用 Java 把它内嵌进自己的服务、和业务代码同进程、用它强大的约束评分和元启发式求解，用它。

一个我会实际采用的混合架构是：Java/Spring Boot 做主系统和业务编排，把"全网络、多层级的主计划"通过 REST/DB 交给 frePPLe 引擎算；当某个瓶颈车间需要更精细的排序时，Java 侧用 Timefold 对这一个子问题建模（输入来自 frePPLe 导出的净需求和交期），算出更优的工序顺序后，再以 operationplan 的形式写回。这样既不用 Java 重造预测/库存/DRP 的轮子，又能在最需要的点上用上 Java 生态的优化器。语言从来不是壁垒，**把正确的计算放在正确的引擎里**才是架构能力。

## 踩过和预见的坑，一并给你

- **文档会过时，代码是唯一事实来源。** 我在这个系列里多次遇到"文档/旧参数 vs 现版代码"的差异：`plan.planSafetyStockFirst` 参数 2024 年已被迁移删掉、planType 的准确语义写在 solver.h 注释里而不是营销页。读开源代码，永远以能编译运行的那一份为准。
- **垃圾主数据进，垃圾计划出。** 求解器再强，也救不了没维护产能日历、提前期随手填、替代关系缺失的数据。上线前花在清洗主数据上的时间，远超调算法的时间。
- **三种计划模式都要跑，问题报告必须看。** 无约束计划的全部价值在 Problem 红标里，只看甘特图等于自欺。
- **先建直觉再啃内核。** 用容器跑起来、手工建几个物料和工序点一次"生成计划"，再带着问题去读 C++，比一上来硬啃 ask-reply 高效十倍。
- **给数据兜底。** 层级成环、无效日历、配不出补货来源的 Buffer，引擎会报 InvalidData/AwaitSupply 而不是崩溃，但你应该在导入侧就拦住。
- **打好基线标签。** 我下载完第一件事就是打基线 commit，之后每次怀疑"这是原设计还是我改坏的"，一条 diff 就是答案。

## 写在最后

回头看这十章，frePPLe 教给我的其实远不止一个排程算法。我看到一个 C++23 的硬核计算内核怎样克制地只做热计算、把事务和界面留给 Python；看到 BOM 和工艺路线怎样在"工序"这一个概念上优雅统一，让多层展开成为递归的自然结果；看到 ask-reply 这种局部问答协议怎样涌现出全局计划；看到问题标记和供需追溯怎样让一个启发式算法重新变得可解释、可问责；也看到用一整个数据库做沙箱这种"笨办法"背后的工程可靠感。

更重要的是，它让我对"供应链计划是最上游的决策"这句话有了实感：下游 WMS、TMS 里那些救火式的忙碌，很多在计划桌前就已经注定。计划备多备少、早排晚排一个决策，会被执行系统放大成十倍的库存或十倍的催货。学会在这个层面思考，是一个后端工程师从"实现功能"走向"理解生意"的关键一步。

我没有因为语言不同就绕开它，这是这个系列我最想传递的态度：**真正的工程壁垒从来不是某门语言的语法，而是领域模型和算法思想。** 愿你也能跨过语言那道心理门槛，从这套优秀的开源代码里，拿走比代码本身更值钱的东西。

全系列到此结束。计划已经算好，剩下的，交给车间和仓库去执行。
